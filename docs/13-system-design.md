# 13 · 算法系统设计

> 「设计一个推荐系统」「设计一个 RAG 问答系统」是算法岗后期面试（三面 / 交叉面 / 主管面）的高频开放题。
> 它考的不是你会背多少模型，而是**能不能把一个模糊需求拆成可落地的系统，并对每个取舍说出理由**。

## 本章高频考点

> 星级是**主观判断**，反映常见面经里的印象分布，不是统计数据。用来排复习优先级即可。

| 考点 | 频率 | 典型问法 |
|---|---|---|
| 通用答题框架 | ★★★ | 面对任何开放设计题的第一步 |
| 推荐系统设计 | ★★★ | 从 0 设计一个短视频推荐 |
| RAG / LLM 应用设计 | ★★★ | 设计一个企业知识库问答 |
| 特征平台与训练-推理一致性 | ★★★ | 怎么保证线上线下特征一致 |
| 在线服务的延迟与容量 | ★★ | QPS 多少？P99 延迟怎么保证？ |
| 模型更新与回滚 | ★★ | 模型多久更新？出事怎么回滚？ |
| 冷启动与降级 | ★★ | 依赖挂了返回什么？ |

## 1. 通用答题框架（先背这个）

开放题最怕上来就讲模型。正确的顺序是**先问清楚，再定指标，最后才是技术方案**：

```
1. 澄清需求   →  谁用？什么场景？规模多大？延迟要求？
2. 定义指标   →  北极星指标 + 护栏指标 + 离线代理指标
3. 数据       →  有什么数据？怎么埋点？标签怎么来？
4. 整体架构   →  画框图，标出每个模块的输入输出和量级
5. 逐模块细化 →  面试官会挑一个让你深入
6. 工程约束   →  延迟、容量、成本、可用性
7. 上线与迭代 →  AB 实验、监控、回滚、下一步优化
```

**第 1 步最容易被跳过，但它是拉开差距的地方。** 一定要问出来的问题：

- 用户规模、物品规模、日请求量（决定架构复杂度）
- 延迟预算（决定能不能用大模型）
- 是冷启动阶段还是已有大量数据（决定要不要先做规则版）
- 优化什么（点击？时长？成交？留存？—— 决定整个系统的目标函数）

**一个好答案的标志**：每做一个技术选择，都主动说出「为什么不选另一个」。

## 2. 指标体系怎么定（几乎必问）

| 层级 | 作用 | 例子 |
|---|---|---|
| **北极星指标** | 业务真正要的，唯一 | 人均有效播放时长 / GMV / 7 日留存 |
| **护栏指标** | 不能变差的底线 | 多样性、创作者生态、广告收入、P99 延迟 |
| **代理指标** | 能快速离线迭代的 | AUC / GAUC / Recall@K / NDCG |

**核心张力**：代理指标涨不等于北极星涨（见 [05 §6.2](05-recsys-ads.md) 的「离线涨线上不涨」七条原因）。
所以设计题里要主动说：**代理指标只用于快速筛选方案，最终以 AB 实验的北极星指标为准。**

**指标劫持要警惕**：只优化 CTR 会催生标题党；只优化时长会推低质长视频。
所以护栏指标不是走过场，是防止系统被自己的目标函数带偏。

## 3. 推荐系统设计（最经典的题）

### 3.1 五分钟版本的完整回答

**需求澄清** → 假设：短视频 App，日活千万，物品库亿级，端到端延迟预算 200ms，优化人均有效播放时长。

**指标** → 北极星：人均有效播放时长；护栏：次留、内容多样性、创作者曝光基尼系数；代理：GAUC、时长回归 MAE。

**架构**：

```
                        ┌── 用户请求（含 user_id, 上下文）
                        ↓
              [ 特征服务 ]  用户画像 / 实时行为序列 / 上下文     ~10ms
                        ↓
   [ 召回 ]  多路并行，亿级 → 千级                              ~30ms
     · 双塔向量召回（ANN，HNSW）      · ItemCF / Swing
     · 用户长短期兴趣召回              · 热门 / 新品探索池
                        ↓
   [ 粗排 ]  轻量模型，千级 → 百级                              ~20ms
                        ↓
   [ 精排 ]  多目标模型（MMoE/PLE），百级 → 几十                ~60ms
                        ↓
   [ 重排 ]  多样性打散 / 疲劳度 / 业务规则 / 广告混排           ~10ms
                        ↓
                     返回 Top-N
```

**为什么分层** → 算力与效果的权衡，见 [05 §1](05-recsys-ads.md)。

**多目标融合** → 精排出 pCTR、p完播、p点赞、p时长，融合公式
$\text{score}=p_{ctr}^{\alpha}\cdot p_{finish}^{\beta}\cdot(\text{时长})^{\gamma}$，
权重靠线上 AB 调，不要拍。

**数据链路**：

```
客户端埋点 → Kafka → 实时流（Flink）→ 特征快照 + 实时特征
                  └→ 离线数仓（Hive/Iceberg）→ 天级样本 → 训练
```

**关键点**：训练样本用**线上打分时落盘的特征快照**，而不是离线重新算 —— 这是防止特征穿越和线上线下不一致的根本手段（见 [05 §4.3](05-recsys-ads.md)）。

### 3.2 面试官必然追问的几个点

**「亿级物品怎么做到 30ms 召回？」**
物品向量离线算好灌进 ANN 索引（HNSW），线上只算用户塔一次前向 + 一次 ANN 查询。
多路召回并行发起，取并集。索引分片 + 多副本扛 QPS。

**「实时性怎么保证？用户刚看完一个视频，下一刷能反映吗？」**
三个层次：① 实时行为序列走 Redis/Feature Store，秒级可见；
② 实时特征（近 5 分钟的 item CTR）走 Flink 流式计算，分钟级；
③ 模型参数走增量训练（online learning 或小时级增量），小时级。
不要说「全都实时」—— 成本和稳定性都不允许，要说清哪一层实时到什么程度。

**「新用户/新视频怎么办？」** → [05 §5](05-recsys-ads.md) 冷启动三层解法。
设计题里要额外强调**探索流量池**：给新内容固定比例的曝光配额，否则系统会陷入马太效应，永远学不到新内容的真实质量。

**「某一路召回挂了怎么办？」**
降级策略：多路召回本身就是冗余，单路超时直接丢弃该路结果；
全部召回挂了 → 返回热门兜底列表（本地缓存）；精排挂了 → 用粗排分数直接出。
**能主动讲降级和兜底，是工程成熟度的信号。**

**「模型多久更新？出问题怎么回滚？」**
Embedding 和稀疏参数增量更新（小时级），全量模型天级。
上线走小流量 → 观察核心指标 → 逐步放量。每个版本保留可回滚的 checkpoint，
监控到指标异常自动切回上一版本。

## 4. RAG / LLM 应用系统设计

### 4.1 企业知识库问答的完整设计

**需求澄清** → 文档量级？更新频率？要不要引用溯源？延迟能接受几秒？有没有权限隔离？错答代价多大？

**指标** → 端到端：答案正确率（人工/LLM 评）、拒答率、引用准确率；
分段：检索 Recall@k / MRR，生成 faithfulness；工程：TTFT、P99、单次成本。

**架构**：

```
【离线】文档 → 解析(PDF/表格/图) → 清洗去重 → 切分 → 向量化 → 向量库 + 倒排索引
                                                        ↑ 增量更新 + 版本管理

【在线】query → 权限过滤 → 查询改写(多查询/HyDE)
             → 混合检索(向量 + BM25) → RRF 融合 → Cross-Encoder 重排 top-5
             → 拼 prompt（含引用要求）→ LLM 生成 → 引用校验 → 返回
```

各环节的优化手段见 [04 §7](04-llm.md)。设计题里额外要讲的是：

**权限隔离** —— 企业场景的关键。必须在**检索阶段**就按用户权限过滤（向量库带 metadata filter），
不能等生成完再过滤 —— 那时信息已经泄漏进上下文了。

**文档更新** —— 增量索引 + 版本号。删除的文档要真删（或标记不可见），
否则会答出已废弃的政策。

**成本与延迟** —— 重排用 Cross-Encoder 准但慢，只对 top-50 做；
高频问题走语义缓存；长 system prompt 用 prefix caching。

**兜底** —— 检索不到相关文档时**明确拒答**并给出人工入口，不要让模型硬编。
拒答率本身是要监控的指标：太高说明检索差，太低说明在幻觉。

### 4.2 「怎么评估这个系统好不好」

这是 RAG 设计题最容易答砸的地方。正确回答分三层：

1. **检索层**：构造 (query, 相关文档) 标注集，看 Recall@k、MRR、NDCG。
   这层能自动化、能快速迭代。
2. **生成层**：faithfulness（答案是否有出处支撑）、answer relevance、context precision。
   可用 LLM-as-a-Judge，但要注意位置偏见和长度偏见（见 [04 §9.3](04-llm.md)）。
3. **端到端**：人工标注一个几百条的黄金集，定期回归。
   **线上还要看用户行为**：追问率、复制率、点踩率、转人工率。

**评测集怎么来** —— 从真实用户 query 采样 + 领域专家标注，不要用 LLM 生成的合成问题当主力，
那和真实分布差很远。

## 5. 特征平台与训练-推理一致性

这是算法工程系统设计里最有区分度的话题，因为它是实践中真正踩坑的地方。

**问题**：离线训练用 Python/Spark 算特征，线上推理用 Java/C++ 算，两套代码 → 必然不一致 → 线上效果暴跌。

**三种解法，从弱到强**：

| 方案 | 做法 | 优缺点 |
|---|---|---|
| 双写对齐 | 两套代码，定期 diff 抽样校验 | 简单，但迟早会漂 |
| **特征快照** | 线上打分时把用到的特征原样落盘，训练直接消费这份 | **从机制上保证一致**，主流方案 |
| 统一特征定义 | 用一套 DSL 定义特征，离线/在线共用一份编译产物 | 最彻底，工程投入大（Feast / 内部特征平台） |

**面试要点**：能说出「特征快照」这四个字，并解释它为什么从根本上消除了不一致，
比列举一堆模型名字更能证明你真的做过。

**还要注意**：
- 特征的**时间语义**：统计特征必须严格用事件时刻之前的数据，否则穿越（见 [05 §4.3](05-recsys-ads.md)）
- 特征的**版本管理**：改了一个特征的定义，历史样本要不要重算？通常是加新特征而不是改旧的
- 特征**监控**：线上特征的分布漂移要告警，缺失率突增往往是上游埋点挂了

## 6. 在线服务的工程约束

### 6.1 容量估算（面试官爱让你现场算）

给定：日活 1000 万，人均每天 20 次请求，峰值是均值的 3 倍。

```
日请求量 = 1000万 × 20 = 2 亿
平均 QPS = 2亿 / 86400 ≈ 2300
峰值 QPS ≈ 2300 × 3 ≈ 7000
```

单机能扛多少？假设精排单次 50ms、8 并发 → 单机 160 QPS → 需要约 45 台，
再乘冗余系数 2 → **约 90 台**。

**这类估算不要求精确，要求有量级感和推导过程。**

### 6.2 延迟预算怎么分

端到端 200ms 的预算要拆到每个模块（见 §3.1 的架构图）。原则：
- 用 **P99** 而不是平均值做预算，长尾才是用户体感
- 能并行的一定并行（多路召回、多个特征源）
- 给每个下游设**超时**，超时即降级，绝不无限等待
- 预留 20% 余量给网络抖动和 GC

### 6.3 LLM 服务的特殊性

见 [04 §3](04-llm.md)。设计题里要讲清：
- **TTFT 和 TPOT 是两个不同的指标**，对话场景优先 TTFT（首字出得快，体感就好）
- **延迟和吞吐是矛盾的** —— 增大 batch 提吞吐但拉高单请求延迟，按场景取舍
- 流式返回（SSE）能大幅改善体感，即使总时长不变

## 7. 常见开放题的回答骨架

| 题目 | 关键点 |
|---|---|
| 设计一个搜索引擎的排序 | Query 理解（纠错/改写/意图）→ 召回（倒排 + 向量）→ 排序（相关性 + 质量 + 个性化）→ 多样性；相关性和个性化的权衡 |
| 设计一个反作弊系统 | 强对抗性 → 规则 + 模型双层；样本极不平衡；标签延迟且有噪声；要能快速迭代对抗新手法；误伤代价高，需人工申诉通道 |
| 设计一个广告投放系统 | ECPM 排序、GSP 拍卖、预算平滑、oCPC、校准比排序更重要、延迟反馈（见 [05 §8](05-recsys-ads.md)） |
| 设计一个 AI 客服 | 意图识别 + FAQ 检索 + LLM 生成三层；能确定回答的走检索，兜不住的转人工；**关键是设计好「不确定就转人工」的阈值** |
| 设计一个内容审核系统 | 多模态（文本/图/视频）；分级处置（放行/降权/人审/封禁）；召回率优先于精确率；模型 + 人审闭环产生新标签 |
| 把线上模型的延迟降一半 | 先 profile 定位瓶颈 → 模型侧（蒸馏/剪枝/量化）+ 工程侧（算子融合/批处理/缓存）+ 架构侧（粗排前置/提前截断） |

## 8. 加分与扣分

**加分**
- 主动澄清需求，而不是直接开讲
- 每个选择都说「为什么不选另一个」
- 主动提降级、兜底、监控、回滚
- 承认不确定：「这块我没实践过，我的理解是…，可能的风险是…」
- 用量级感说话（亿级/千级/百级、ms 级）

**扣分**
- 上来就堆模型名字，不问场景
- 所有环节都说「用大模型」，不考虑延迟和成本
- 只有离线指标，不提 AB 实验
- 画了架构图但说不清每个模块的输入输出和数据量级
- 被追问一层就崩，说明只是背过架构没想过为什么
